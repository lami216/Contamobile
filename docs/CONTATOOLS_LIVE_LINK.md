## إعدادات المصدر العام

الخدمة `https://3ali.store` ومفتاح الاستعادة العام
`0d224040-8d24-4f18-9b3e-052fe2016a6f` محفوظان في
`approved-android/contatools-public.json`. أكّد المالك أن التصدير من الخدمة الحالية.
لم تُولّد مفاتيح أو حساب إدارة. فحص القراءة تحقق من HTTPS وHSTS واستجابة الخدمة؛
مسار المفاتيح المحمي يعيد 401 دون جلسة إدارة، ولم تُنفّذ استعادة حية أو موافقة
إدارية على عميل. نجاح health لا يثبت الربط الوظيفي.

يتحقق Gradle من وجود عنوان HTTPS ثابت ومفاتيح P-256 عامة فقط. إنشاء مرشح
Release يتطلب `ALKARNA_HIGHEST_DISTRIBUTED_CODE` المؤكد من المالك، و
`ALKARNA_PREVIOUS_APK_SHA256`، ورقم/اسم إصدار صريحين؛ ويرفض رقمًا لا يزيد عن
أعلى موزع، أو إعدادات تختلف عن المصدر العام المعتمد. القيمة القديمة الافتراضية
14 تُستخدم لجمع الكود فقط؛ لا تسمح بوابة المرشح بتحويلها تلقائيًا إلى ملف توزيع.

المالك لا يعرف أعلى versionCode حاليًا. يلزم آخر APK موزع وتأكيد أنه الأعلى
قبل بناء المرشح أو اختبار التحديث. لا يوجد APK جديد في هذه المرحلة، ولا يجوز
تسمية اختبارات المصدر/JVM أو ملفات APK السابقة اختبارًا لمرشح جديد.

## الاتصال والرفع

| الحدث | السلوك | HTTP في المسار الناجح |
| --- | --- | --- |
| أول تسجيل | jitter محفوظ 30–180 ثانية أثناء ظهور التطبيق والشبكة | 2: challenge ثم dispatch |
| فتح/استئناف/شبكة متذبذبة بلا تغيير | دمج أحداث، ثم نتيجة محفوظة دون رفع | 0 |
| تغير الإصدار أو الترخيص الأصلي أو المحل/المالكين | debounce ثم تسجيل واحد بهوية التثبيت نفسها | 2 |
| تناقص الوقت فقط | لا يغيّر البصمة ولا يطلق تسجيلًا | 0 |
| انقطاع الشبكة/إخفاء التطبيق | إيقاف المؤقتات؛ الاستئناف عند عودة الاستخدام/الشبكة | 0 أثناء التوقف |
| خطأ مؤقت في التسجيل | backoff يبدأ 15–30 ثانية ويتضاعف مع jitter حتى 6 ساعات؛ يحترم Retry-After | حتى 2 لكل محاولة؛ قد يفشل الأول وحده |
| رفض دائم للتوقيع/الترخيص/الإعداد | إيقاف المحاولات التلقائية لنفس البصمة | 0 حتى تغير مهم أو تدخل مناسب |
| استعادة يطلبها المستخدم | تتجاوز jitter الأول؛ تحترم حدود الخادم وإعادة المحاولة اليدوية | التسجيل 0 إن كان محفوظًا؛ ثم 2 للطلب |
| طلب استعادة ينتظر الموافقة | استعلام كل 45 ثانية مع نافذة ظاهرة، وتحديث يدوي بحد أدنى 10 ثوانٍ | 2 لكل استعلام |
| فشل استعلام الاستعادة | backoff يبدأ 30–60 ثانية ويصل إلى 15 دقيقة؛ توقف عند الرفض الدائم | لا تداخل بين الطلبات |
| الرفض/الانتهاء/الاكتمال/إغلاق النافذة | إيقاف استعلام الحالة | 0 |
| تأكيد حفظ كلمة المالك | الحفظ المحلي والإيصال أولًا؛ تأكيد الخادم مستقل مع retry محفوظ | 2 لكل محاولة تأكيد لازمة |

التسجيل الواحد ليس طلب HTTP واحدًا. الحد الأدنى لاستعادة جهاز مسجل مسبقًا،
مع استعلام واحد يعيد الموافقة، هو 8 طلبات: الطلب والاستعلام والـclaim والـcompletion،
كل منها challenge + dispatch. التسجيل الأول يضيف طلبين، وكل استعلام إضافي يضيف
طلبين؛ فقد الرد قد يضيف محاولات أخرى مع بقاء الأثر idempotent.

لا heartbeat أو WebSocket أو polling عام أو WorkManager أو foreground service.
مراقب الشبكة موجود أثناء ظهور Activity فقط، وصف العمل أصغر من 9 مهام وبعامل واحد
مشترك داخل العملية؛ يتوقف خيطه بعد الخمول. لا يوجد وعد بالتسجيل والتطبيق مغلق.
وقت أول ظهور في الأداة مستقل عن بداية التفعيل. حالة/مدة الترخيص في اللوحة لقطة
يبلغ عنها الهاتف عند آخر رفع؛ لا تُعرض كمدة تاريخية تحقق منها السيرفر أو كحضور حي.

## الحالة المحلية والاستعادة

يحفظ سجل `contatools-v1.json` الموثّق والمشفّر أصلًا إصدار البروتوكول، بصمة
الحقول المستقرة، آخر نجاح، محاولة معلّقة وموعدها، الفشل الدائم وRetry-After.
لا يشمل حسابات المحاسبة أو سجلاتها، ولا يُستبدل بسجل قاعدة بيانات المحل.
المهام المحلية عند فتح المحاسبة لا تنتظر استجابة شبكة معلّقة.

لم تتغير applicationId أو الشهادة المثبتة أو أصل WebView أو قاعدة البيانات أو
ملفات التفعيل ومفاتيحه ومدته. الطلب يستهدف المالك المحلي المسجل فقط. التغيير
يستخدم الإذن والـclaim الموقّعين والإيصال الأصلي أحادي الاستخدام؛ يغير كلمة المالك
وجلساته دون العاملين، ولا ينشئ جلسة مالك تلقائيًا. تأخر completion لا يمنع المحاسبة.

## قائمة الحقول الصادرة كاملة

الغلاف الأول: `operation`, `payload`.
الغلاف الثاني: `operation`, `payload`, `challengeId`, `signature`.

`register.payload` فقط:

- `installationId`، و`publicJwk` العام (`kty`, `crv`, `x`, `y`).
- `licenseDocument` الأصلي الموقّع: `schema`, `version`, `keyId`, `algorithm`,
  `payload`, `signature`. حمولة v1: `licenseId`, `storeId`, `customerName`,
  `storeName`, `deviceId`, `edition`, `type`, `issuedAt`, `notes`.
  حمولة v2 تستخدم `durationSeconds`, `activationMode` بدل `issuedAt`.
- `deviceCode`، وهو كود الجهاز المستخدم للتفعيل، لا رقم هاتف العميل.
- `applicationId`, `appVersion`, `versionCode`.
- `localShopId`، و`owners` (لكل مالك: `id`, `name`, `role=owner`).
- `activation` (`valid`, `remainingSeconds`, `status`) كمعلومة يبلغ عنها العميل.

عمليات الاستعادة تستخدم `installationId`, `shopId`, `ownerId`, `requestId` فقط؛
ويضاف `grantId`, `intentId` إلى claim/complete. لا يُرسل مستند الترخيص مع كل
استعلام. كلمة المرور الجديدة وPBKDF2 والسجل المالي والمفاتيح الخاصة لا تخرج من الهاتف.

## الفحوص وحدودها وخطوة التسليم

الفحوص المتاحة دون إصدار APK: سياسات Java الفعلية على JVM، timers/single-flight
بساعة فحص، متجهات البصمة، فحوص مصدر المحاسبة والترجمة والاستيراد، جمع Java بالكامل
واختبارات JVM، وفحص بوابة رفض مرشح بلا baseline. هذه لا تثبت تحديث APK فعليًا.

بعد وصول APK السابق وأعلى رقم وتحديد جهاز/ترخيص فحص مخصص بإذن المالك:
نبني مرشحًا واحدًا بالتوقيع الدائم، نفحص إعداداته من البايتات باستخدام
`verify-contatools-apk.py` مع فحص التوقيع والنسخة، ونختبر تحديث البيانات/المالك/
العامل/المدة والتسجيل ثم الاستعادة الحية على HTTPS. نسجل SHA-256 وشهادة التوقيع
والنسخة والنتائج ونختبر الملف نفسه على هاتف المالك. لا توزيع أو دمج تلقائيًا،
وأي إصلاح ينتج بايتات جديدة يحتاج إعادة اختبار. التفعيل الأول والتجديد والتعليق
والنقل والمدفوعات خارج هذه المرحلة.
