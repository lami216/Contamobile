## عقد الدلتا

يرسل العميل الجديد `clientProtocol` في إثبات الدخول. يعلن الخادم `protocolCapabilities.sharedDeltaVersion:1` و`salesViewVersion:1`. قبل الإعلان يستخدم العميل المسار القديم. العملاء الحاليون ذوو صلاحيات القراءة القديمة يستمرون دون تغيير. الحساب المقيد يحتاج عميلًا يعلن قدرته على العرض المحدود.

`online.bootstrap` مع `viewVersion:1` يرجع organizationId/branchId/epoch/cursor/view/state/viewHash. يحتفظ العميل بالحالة المرجعية في RAM فقط. `online.delta` يطلب التغييرات التالية؛ كل صفحة تقيد المنشأة والفرع والموضع والعرض، وكل patch له beforeHash/afterHash، وتحديثات upserts/deletes وترتيب صريح عند تغير ترتيب الصفوف، واستبدالات scalar محددة. لا يعتمد العميل موضع الصفحة أو العرض حتى اكتمال جميع الصفحات والتحقق منها. يحفظ materializeLocalView تخصيص المعرفات المحلية دون إعادة استعمال المعرفات المحذوفة.

اختلاف epoch أو خروج الموضع من نافذة الاحتفاظ يستدعي snapshot صريحًا. فشل الشبكة يحفظ آخر موضع مؤكد. فشل التحقق أو تبني العرض يمنع الاستخدام ويطلب إعادة تهيئة العرض؛ لا يحوّل حالة قديمة إلى حالة متصلة. أي تغير للصلاحيات، بما فيه أول فحص بعد الدخول، يمسح العرض المميز قبل عرض الدور الجديد.

الإيصال المطابق لمعرف العملية وبصمتها هو حد نجاح البيع. فشل قراءة لاحقة أو تبني واجهة لا يحوّل بيعة مؤكدة إلى فشل، ولا ينشئ UUID بديلًا. تبقى نية pending والإيصال وACK الأصلية في التخزين الأصلي المحمي، ويستأنف الرد المفقود بالمعرف نفسه.
