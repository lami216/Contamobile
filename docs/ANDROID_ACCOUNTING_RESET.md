# Owner-consented local accounting reset

The Contatools administrator may request a clean start on one approved Android installation running versionCode20 or later. No production deployment is part of this change.

The administrator identifies the exact local shop and owner, verifies ownership, records a reason and creates a request valid for at most24hours. Merely receiving/polling a request never deletes data. Only the matching logged-in local owner sees an acceptance checkbox and destructive confirmation. Other staff cannot accept. Before login the phone may display an informational notice asking the owner to sign in. Decline and defer are separate choices. A request can be cancelled administratively only before it has been claimed.

The existing installation Keystore signature proves the phone; pinned Contatools signatures authorize a separate accounting-reset purpose. The phone persists an explicit accepted intent before sending its claim. A lost response resumes that same intent. Generic HTTP errors never prove cancellation: only an exact signed unclaimed denial, or authoritative local absence of an intent, releases the pending screen. A previously accepted but unresolved operation blocks further accounting until reconciled. Normal users with no reset intent retain fully offline startup and use; no reset state is created merely by checking that none exists.

After a verified claim, native backup staging is paused for the whole shop, old password recovery is invalidated and the server revokes old cloud upload consent/pending generations. The single IndexedDB transaction removes products, stock, parties, balances, invoices, history, cached local snapshots, user verifiers, sessions and business metadata. It writes an empty valid shop with the same originId, advances the revision, and retains only non-secret reset/recovery single-use receipts, an epoch barrier and a bootstrap record for the original owner identity. If the transaction aborts, all old data remains. Other windows with stale revisions cannot resurrect it.

Only after the database commit and local draft/session cleanup does the phone durably consume the native grant. A server acknowledgement can retry independently without repeating the local wipe. After reboot/reopen the original device license remains valid with the same remaining time. The setup screen uses verified license customer/shop names and asks only for a new username and PIN/password of at least4characters. The original ownerId/shopId remain; old credentials and worker accounts do not. Initial account creation atomically consumes the bootstrap marker. A replayed reset receipt cannot remove newly entered accounting or clear a recreated owner's new persisted draft.

No activation key/state, issuer, package ID, permanent signing identity or license clock is changed. No Android reinstall or app-data clear occurs. Files the owner previously exported outside the app and completed cloud backup versions remain. Cloud backups require a fresh owner review/consent after the reset; no old cloud copy is automatically restored. Existing cloud-only restoration to a completely blank replacement phone is still outside this change.

Requests arrive when the app is open, foreground and connected; there is no push/background remote-delete service and no compulsory network heartbeat. Visible polling is bounded to60seconds per local target with backoff. The application can be closed while a confirmed operation is unresolved and resumes safely on reopening. Unrelated corrupted support state must not block a licensed phone that has never accepted any accounting reset; an existing unreadable reset journal remains fail-closed.

Verification includes real-browser transaction abort/replay/stale-writer/old-password-grant/consent/decline/French/keyboard-sheet checks, signed native purpose/scope tests, six isolated Android scenarios including real IndexedDB reset and activity reopen, and install-over-existing preservation for original distributed APKs. All fixtures are disposable and excluded from production.
