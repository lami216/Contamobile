# Optional Android server backups

This feature copies a consistent, already committed local accounting snapshot. It
does not synchronize edits between devices and is never part of an accounting
transaction. A server outage, expired backup subscription, quota error or disabled
backup does not change local data, passwords or the device's activation period.

## Activation and consent

Contatools must approve the registered installation and enable its separate backup
subscription. The owner must then opt in on the phone while online. Registration
alone does not upload anything. Once consented, subsequent committed accounting
changes can be staged while a cashier is signed in; the staging scope remains the
consented business and owner. A different business cannot replace that scope while
it is active.

Turning automatic backup off stops the local job immediately, including offline.
The revocation request is retained until connectivity returns. A restore, import or
merge additionally invalidates the staged and pending upload and increments its
local generation. Resuming after a local replacement requires explicit consent
again; remote consent revocation invalidates the service's previous upload
generation. A request already reaching the service can finish as an immutable old
version; its late response cannot reactivate the locally paused upload.

## Local and transport boundaries

- The application exports only the `alkarna-web-backup` payload: business state,
  users with password digests, schema, creation time and original business ID
  inside `state.originId`. The canonical payload has exactly five root fields.
  Active sessions, native activation files, installation/issuer private keys and
  native recovery journals are outside the payload.
- Staged snapshots and backup metadata are AES-256-GCM encrypted with an independent
  Android Keystore key in the application's private `noBackupFilesDir`. An
  installation fingerprint and file purpose are authenticated. Atomic writes keep
  the previous complete metadata available after a write interruption.
- The fixed HTTPS Contatools origin and existing installation key are used. Every
  operation has a fresh payload-bound signed challenge; backup proofs have a
  distinct protocol schema. This is not a new activation mechanism.
- Each immutable upload has a durable UUID and full SHA-256. Retries after a lost
  response resume the same ID, accepted chunks and commit. A newer local revision
  gets separate staging and cannot mutate the in-flight version. The current
  service limit is 8 MiB per snapshot with 48 KiB raw chunks.

## Scheduling and recovery

Android `JobScheduler` persists one network-constrained job through process death
and reboot. The user may choose upload after changes become staged and connectivity
is available, a daily or weekly preferred local time, and a Wi-Fi-only constraint.
Wi-Fi-only conservatively requires both Wi-Fi transport and an unmetered network;
unmetered cellular is rejected, and metered Wi-Fi waits. Android 9+ jobs include
both requirements; Android 8 jobs use the unmetered scheduling constraint plus the
same explicit transport check before every upload request. New changes are coalesced;
there is no periodic HTTP status heartbeat
or full-database polling. Network errors retry with bounded exponential backoff,
jitter and applicable server retry deadlines. Manual backup uses the same durable
upload and does not create duplicate versions when nothing changed.

The preferred time is approximate. Doze, battery restrictions, network availability
and operating-system quotas may delay execution. A missed schedule is caught up
when its constraints permit. User force-stop can prevent background work until the
app is opened again. The latest committed changes are staged shortly after a save;
an abrupt process kill before staging completes is recovered by staging from the
durable database on the next app opening.

Downloaded versions are bounded, verified chunk by chunk and checked against their
full SHA-256 before being handed to the existing restore preview. Downloading never
replaces local data. An explicitly transferred subscription can expose a backup
whose original shop identity differs from the new installation; that original
identity is preserved for the existing preview/restore decision. Restoring a data
backup does not restore or extend activation.

## Verification

`scripts/test-cloud-native-adapter.mjs` exercises acknowledged chunk backpressure,
intact bytes, native error metadata, lost begin/chunk confirmations, size limits and
page lifecycle cancellation. `CloudBackupPolicyTest` covers settings, local-time
daily/weekly timing, daylight-saving changes, backoff, revision order and payload
boundaries.

The unit resource `cloud-snapshot.json` was generated by executing the real
`ShopDatabase.cloudSnapshot` in Chromium, including its actual password-digest
format; native validation consumes those emitted bytes rather than a separate
invented envelope.

`CloudBackupTest` is an emulator-only instrumentation fixture that skips an existing
backup staging area. It uses a signed in-memory service and real Keystore, private
encrypted files and JobScheduler. Its six scenarios cover consent/scope/stale
staging and pause, lost commit responses across manager recreation with a newer
snapshot, verified transferred downloads and tamper rejection, server generation
invalidation without losing local staging, Wi-Fi/cellular transport restrictions,
and an actual
operating-system JobService run without an Activity or WebView. It makes no request
to the production service. Instrumentation results must be taken from the candidate
build's emulator run; the existence of the tests is not execution evidence.

Android scheduling behavior: [JobScheduler reference](https://developer.android.com/reference/android/app/job/JobScheduler)
and [JobInfo.Builder reference](https://developer.android.com/reference/android/app/job/JobInfo.Builder).
