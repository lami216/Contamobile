# Android account access — interaction plan

The approved Arabic/French WebView ledger remains the accounting interface. The new entry page asks for one identifier and one secret. An email identifies a shared institution and requires a live connection; a Mauritanian phone number (eight digits beginning 2, 3 or 4) requests approval for this exact local installation. The disclosure and privacy link appear before submission. No price, payment link or purchase invitation appears.

Pending approval is explicit: check status, then deliberately install the approved activation. A valid existing local license has a separate entry leading to the unchanged local user login. Linking existing accounts is available only to the authenticated local owner and sends that exact owner/shop scope. It cannot select an arbitrary owner or reset a password.

Online institutions use an isolated in-memory store. A connection gate masks ledger data, disables ledger actions and preserves current form/cart drafts whenever admission cannot be freshly checked. Shared writes are semantic accounting commands: display success only after an authoritative matching receipt. An uncertain result keeps its original identity and must be checked before another write. A rejected/conflicting result retains the form and requires review; it never becomes an automatically retried new transaction. Local backup, reset, owner recovery and user management are not institution shortcuts.

Controls have visible labels, at least 44px targets, logical RTL/LTR layout, a clear busy/error state and no secret persistence in browser storage. Privacy opens in the native policy screen. Offline mode preserves the existing database name, owner verifier, shop identity, license and clock. Fresh approved local accounts derive the existing PBKDF2 verifier from the transient entered secret and discard that secret after setup.

Validation covers identifier boundaries, exact local binding, cross-branch bootstrap rejection, receipt hash and operation matching, duplicate-safe pending reconciliation, rejection/timeout behavior, semantic action encoding, and storage separation. Parent integration covers native proofs, device testing and APK packaging. API 36 and privacy content are owned by the parallel readiness change.

Support copy describes problems with login or application use in both languages. It does not invite a purchase or promote external activation payments. The existing technical local-license file/status controls remain available to preserve installation and renewal compatibility.

Terminal receipts remain durable in native storage until the UI acknowledges the exact operation IDs after validating hashes and status. A failed acknowledgment never reverses a known accepted write or reopens its actionable draft. Recovery selects the original pending branch. A stale-epoch rejection, a resolved settlement, or an uncertain request with no native journal leads to a fresh ledger review; prior draft details may be retained read-only in RAM, while live editors/cart and automatic workflow-draft restoration are cleared. A new financial action requires explicit confirmation that the user reviewed the ledger.
