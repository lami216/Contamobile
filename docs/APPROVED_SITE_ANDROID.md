# Approved seller application — Android

The functional local site approved on 2026-10-08 is the presentation and business-behavior reference for this build. `approved-runtime/reference-sha256.json` pins that version. Original Expo/SQLite sources remain available; this APK uses the approved local site's durable IndexedDB stores inside Android WebView. It is intentionally an embedded-web Android application, not a React Native recreation of every screen.

## Interaction plan
Preserve the approved Arabic RTL screens, compact numbered fixed-width tables, 50-row list pages, scroll chaining, semantic dark/light themes (dark default), tolerant Arabic search, invoice filters/details, direct numeric line editors, cash flows in all four directions, opening-stock rules, local users/permissions, backup/import, and full report export. Preserve all current desktop-preview files outside this repository while preparing the APK.

The Android adapter replaces only platform boundaries: external document picker/save dialog for JSON/XLSX/PDF, Android printing, Android back/keyboard/insets, and CameraX plus bundled ML Kit barcode decoding. No localhost process, development server, external site, permission bypass, analytics or runtime download is required. The merged Android manifest removes INTERNET permission. Camera permission is requested only when scanning; manual barcode entry always works.

## Storage and updates
Package `mr.alkarna.mobile.approved` installs alongside the old golden application and has separate local data. Private records and password hashes are never packaged or committed. IndexedDB stores persist across cold launch and app updates with the same package/signature; uninstalling or clearing Android app storage removes them. Export regular backups through the system file picker.

Starting with 1.0.11, all customer releases require the same persistent PKCS12 release key. Its public certificate is pinned in `approved-android/signing-certificate.sha256`. The private key and its passwords live in the repository Actions secret `ALKARNA_SIGNING_BUNDLE`; a separate offline backup must be retained. `scripts/prepare-approved-signing.py` writes it only to temporary runner storage, masks credentials, and the workflow removes that file on exit. Missing credentials or a changed certificate fail the build instead of generating a debug key. Never regenerate the key to fix a missing secret, commit it, upload it in build artifacts, or alter the pin casually.

The 1.0.10 review APK delivered from run 39294721352 had certificate SHA256 `cffdcecc71b02be6984484036014141c54ceeb8ea40f5ee68a67617d0918526e`. Earlier review workflows generated fresh debug keys on ephemeral runners without saving those private keys. The new release key cannot update an APK signed with one of those lost keys. Android signing-key rotation also requires the old private key. A business JSON backup does not transfer native device activation. Do not promise preservation of the old activation across uninstall/reinstall, or silently uninstall a user's installation. Recovering its exact original key would be necessary to update that specific installation in place.

Keep the applicationId, WebView asset origin and IndexedDB name, Android Keystore alias `alkarna.activation.state.v2`, no-backup activation file, and activation preference names unchanged. Ordinary APK replacement with the same persistent signing certificate preserves those stores, Android ID/device code, consumed licenses and remaining activation duration. The update does not require another activation file and must not restart a temporary license's timer.

CI builds a lower-version fixture and the current customer APK using the pinned release key. On an isolated Android emulator, it creates an owner/password, product/opening stock, sale and cash balance, French/light preferences and a temporary activation; force-stops the app; performs a real `adb install -r`; then checks all IndexedDB stores, credentials, device code, native activation, consumed license IDs and remaining duration. No data clear, restore or reactivation occurs between these phases. The fixture is a regression test of the permanent signing identity, not evidence that the old incompatible debug-signed 1.0.10 APK can be upgraded.

## Build
Run `python3 scripts/prepare-approved-android.py`, configure `ALKARNA_KEYSTORE_PATH`, `ALKARNA_STORE_PASSWORD`, `ALKARNA_KEY_ALIAS`, `ALKARNA_KEY_PASSWORD` using the permanent release keystore, then Gradle 8.13 with `gradle -p approved-android :app:assembleRelease`. CI loads those values from its single signing-bundle secret. The workflow `approved-site-apk.yml` verifies the pinned signer of both APKs, runs the real in-place upgrade test, then independently runs the approved seller workflow on an Android 35 emulator with Wi-Fi and mobile data disabled. It checks creation, opening stock, selling, invoice/register rendering, and cold-launch persistence, and publishes screenshots and test reports. Only the verified current APK is uploaded as an installer; signing credentials and the fixture are excluded.

Physical-phone camera, keyboard and printer behavior still require acceptance on the user's device. Emulator tests are evidence of the tested workflows, not a guarantee for every device or every possible accounting sequence.
